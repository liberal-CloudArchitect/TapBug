# 需求分析报告：Hermes 安全检查团队

> 方法：先**完善原始需求**（澄清模糊、补齐约束），再用**第一性原理**逐层拆解到不可再分的原子能力，最后从原子能力**重构**出团队结构与需求清单。
> 日期：2026-07-05 · 配套：`01-信息调研报告.md`、`03-可行性研究与实施方案.md`

---

## 1. 原始需求复述

用户希望封装一个 **Skill**：一个"由 Hermes 系统驱动的网络信息安全检查团队"，通过**不同专家智能体分工合作**，像一个精密协作的团队一样，进行**全流程、多方面**的网络安全检测。使用场景是在 Bugcrowd 学习漏洞挖掘、渗透测试等安全内容。

这段需求方向清晰，但若直接实现会遇到若干未定义点。下面先把它"补全"。

---

## 2. 需求完善（消除模糊、补齐约束）

对原始需求逐项追问 What / Who / When / Boundary / Constraint，得到完善后的需求定义：

### 2.1 目标澄清
| 维度 | 原始表述 | 完善后 |
|------|----------|--------|
| 核心目标 | "全流程多方面网络安全检测" | 对**已授权目标**执行从侦察到报告的结构化安全评估，产出对齐 Bugcrowd VRT 的可提交发现 |
| 交付形态 | "封装一个 skill" | 一个 Claude Code **Skill**（本体 = 编排 + 方法论），内部驱动一组**专家 subagents**，接入 MCP 工具 |
| "团队" | "不同专家智能体分工合作" | 一个 **Orchestrator（Hermes）+ 6~8 个专家 agent** 的角色化团队，按 PTES 阶段协作 |

### 2.2 用户与场景
- **主用户**：安全学习者 / bug bounty 猎人（当前使用者本人）；
- **典型场景**：拿到一个 Bugcrowd 授权 scope（域名/资产清单），希望团队自动推进"侦察→攻击面测绘→漏洞识别→可利用性验证→报告"，并在关键决策点征询人类。

### 2.3 边界（明确"不做什么"）
- **不做**：未授权目标测试、破坏性攻击（DoS）、数据外泄、持久化驻留、越权扩大访问、绕过检测以规避防御；
- **不做**：全自主无人值守的高危利用——高风险动作强制 HITL；
- **做**：侦察、枚举、脆弱性识别、**最小 PoC** 验证、影响评估、报告与知识沉淀。

### 2.4 关键约束（按优先级）
1. **合规/法律**（最高，一票否决）：仅在显式 scope 内行动；遵循 Bugcrowd Safe Harbor 与最小 PoC 原则；
2. **安全护栏**：scope 校验、危险命令拦截、防 prompt injection；
3. **可审计**：每一步动作可追溯（谁、何时、对什么、做了什么、结果）；
4. **可控成本**：LLM 调用与工具运行的时间/费用可预期；
5. **可扩展**：新增专家 agent / 新工具的成本低。

## 3. 第一性原理拆解

第一性原理要求：不从"别人怎么做团队"类比，而是从**最基本的事实**出发，问"安全检测这件事，本质上到底在解决什么？"，再重构。

### 3.1 第一问：安全检测的本质是什么？

> **本质**：安全检测是在**信息不对称**下，系统性地**发现攻击面**并**验证其可利用性**，从而把"未知的风险"转化为"已证明、可修复的发现"。

拆开这句话，得到三个不可回避的基本事实：
- **F1｜攻击者视角**：只有以攻击者视角枚举入口，才能发现防守者看不见的路径；
- **F2｜验证优于猜测**：一个漏洞的价值在于**被证明可利用**（PoC），而非被怀疑存在；
- **F3｜有限动作原则**：证明影响只需**最小必要动作**——这既是伦理约束，也是第一性事实（多余动作不增加"已证明"的信息量，只增加风险）。

### 3.2 第二问：完成检测需要哪些不可再分的原子能力？

把"全流程检测"一路拆到不能再拆的最小能力单元（原子能力）：

```
安全检测
├─ A1 目标理解与授权确认   （解析 scope，确认边界 —— F3/合规）
├─ A2 信息收集              （子域、资产、指纹、历史数据 —— F1）
├─ A3 攻击面枚举            （端口、服务、路由、参数、认证入口 —— F1）
├─ A4 脆弱性识别            （已知漏洞匹配 + 逻辑缺陷推理 —— F1）
├─ A5 可利用性验证          （构造最小 PoC，观察真实响应 —— F2/F3）
├─ A6 影响评估与分级        （对齐 VRT/CVSS，判定业务影响 —— F2）
├─ A7 报告生成              （复现步骤、证据、修复建议 —— F2）
└─ A8 知识沉淀              （经验/payload/教训写回记忆 —— 复利）
```

这 8 项是**与任何具体工具、任何团队形态无关**的最小集合。任何"安全检查团队"，无论人或 AI，都必须覆盖它们——这是第一性的落点。

### 3.3 第三问：为什么需要"多智能体团队"，而非一个大 agent？

这一步要论证团队结构的**必要性**，而非默认它。从第一性看，多智能体带来四个单体无法同时具备的收益：

1. **上下文隔离**：A2 的海量扫描输出若与 A5 的利用推理挤在同一上下文，会互相污染、稀释注意力。隔离让每个专家在干净上下文中深耕。
2. **专业分工的提示特化**：Web 漏洞、认证授权、API、基础设施各有独立的方法论与 payload 库；一个 agent 的系统提示无法同时对所有领域最优。
3. **并行**：A2/A3 中大量子任务相互独立，可并行压缩时间。
4. **交叉校验与防错**：一个 agent 的结论由另一个 agent（如报告官/合规守门人）复核，降低幻觉与越权。

> 结论：团队结构**不是拟人化的浪漫**，而是从上下文管理、提示特化、并行、防错四个第一性收益推导出的必然选择。

### 3.4 第四问：从原子能力重构团队角色

把 8 项原子能力按"内聚性 + 所需专业知识"聚类，重构出 Hermes 团队（详细职责见方案文档，此处给出映射逻辑）：

| 原子能力 | 归属角色 | 归属理由 |
|----------|----------|----------|
| A1 授权确认 + 全程守门 | **合规守门人 / Hermes 编排层** | 贯穿全程的一票否决，需独立于执行者 |
| A2 信息收集 | **侦察官 (Recon)** | 强工具依赖、可并行、上下文量大 |
| A3 攻击面枚举 | **攻击面测绘 (Attack Surface Mapper)** | 承接侦察，结构化资产/入口 |
| A4 脆弱性识别 | **Web 漏洞 / 认证授权 / API / 基础设施 专家（按域拆）** | 领域知识差异大，需特化 |
| A5 可利用性验证 | **利用验证专家 (Exploitation/PoC)** | 高风险，需最小 PoC + HITL |
| A6 影响评估 | **利用验证 + 报告官 协同** | 分级需证据 + 标准对齐 |
| A7 报告生成 | **报告官 (Reporter)** | 对齐 VRT、面向提交 |
| A8 知识沉淀 | **Hermes 编排层（写记忆）** | 跨会话复利 |

## 4. 需求规格（功能 / 非功能）

### 4.1 功能需求（FR）
- **FR1 授权与 scope 管理**：录入/解析 scope，全程校验目标是否在范围内，越界即阻断。
- **FR2 阶段化编排**：Hermes 按 侦察→测绘→识别→验证→报告 推进，管理阶段间 handoff 与全局状态。
- **FR3 专家分工执行**：各专家 agent 在独立上下文完成本职原子能力，结构化回传结果。
- **FR4 并行调度**：对独立子任务（多子域/多资产）并行分派。
- **FR5 最小 PoC 验证**：仅执行证明影响所需的最小动作，产出可复现证据。
- **FR6 人在环 (HITL)**：高风险动作（利用、可能影响可用性的操作）前暂停征询。
- **FR7 报告产出**：生成对齐 Bugcrowd VRT 的结构化发现（标题、复现、证据、影响、修复、CVSS/VRT 分级）。
- **FR8 知识沉淀**：把有效 payload、方法与教训写回记忆库，跨任务复用。
- **FR9 审计日志**：记录每个 agent 的每步动作与结果，可回溯。

### 4.2 非功能需求（NFR）
- **NFR1 合规性**：默认拒绝越界；内建最小 PoC / 禁外泄 / 禁持久化原则。
- **NFR2 安全性**：危险命令拦截、prompt-injection 防护（借鉴 CAI 护栏）。
- **NFR3 可扩展性**：新增专家 agent / MCP 工具为"加文件 + 注册"，不改核心。
- **NFR4 可观测性**：结构化日志 + 阶段进度可视。
- **NFR5 成本可控**：可设定并行度上限、模型选择、单任务预算护栏。
- **NFR6 可移植**：以 Claude Code 原生机制（Skill + subagents + MCP）为主，减少外部依赖。

### 4.3 优先级（MoSCoW）
| 级别 | 需求 |
|------|------|
| **Must** | FR1, FR2, FR3, FR5, FR6, FR7 · NFR1, NFR2 |
| **Should** | FR4, FR8, FR9 · NFR3, NFR4 |
| **Could** | 局部 swarm 协作、RAG 知识库、benchmark 自评 · NFR5 |
| **Won't（本期）** | 全自主无人值守利用、C2/持久化、检测规避能力 |

## 5. 验收标准（如何判断需求被满足）

1. 给定一个自建靶场/授权 scope，团队能自动完成 侦察→测绘→识别→验证→报告 全流程并产出报告；
2. 对**越界目标**的请求被明确拒绝，且拒绝可解释；
3. 利用类高危动作在执行前触发 HITL；
4. 报告可直接对齐 Bugcrowd VRT 提交格式；
5. 在 XBOW / 自建靶场若干题上跑通并给出可复现结果；
6. 新增一个专家 agent 的改动局限于新增文件 + 注册项。

> 这些标准直接驱动 `03-可行性研究与实施方案.md` 中的架构与路线图。
