## 2. 已验证的事实与测试边界

### 2.1 已执行的无副作用检查

- `excavator` 环境存在，Python 版本为 `3.12.13`。
- 成功导入 `hermes.orchestrator`、`hermes.synth`、`hermes.exploit_agent`；`python -m hermes.orchestrator --help` 正常；全部 `hermes/*.py`、`hermes/scanners/*.py`、`schema/*.py` 和 hook 通过 `py_compile`。
- 审计时没有发现 `test_*.py` 或 `*_test.py`；`excavator` 环境中没有 `pytest`；仓库也没有 `pyproject.toml`、`requirements*.txt`、`environment.yml`、lockfile 或 CI 配置。
- 手动喂给 `hooks/guardrail.py` 的样例中：越界 `evil.example` 返回 `deny`；本地 `curl` 在 dry-run 返回 `ask`；不触网的 Python 命令返回 `allow`。这证明 hook 脚本的几个正向分支可运行，**不证明它已被 Claude Code 安装或覆盖 Python 运行时**。

未运行现有 `hermes.evaluate` 全套：它会覆盖 `bench/scorecard*.md`，并且本地适配器会对固定端口执行 `kill -9`；在没有测试隔离、没有用户授权清理已有进程的前提下，这不是合适的只读审计动作。

### 2.2 运行时真实结构

当前关键调用链是：

```text
Orchestrator
  ├─ Scope.load() / auth()                 # 仅入口目标检查
  ├─ tools.http_probe() / tools.crawl()    # 直接 httpx 请求
  ├─ scanners.run_all()                    # ThreadPool 并发函数调用
  ├─ tools.verify_candidate()              # 再次直接请求
  ├─ 直接写 findings、report、state、knowledge、audit
  └─ 可选 ctf / exploit_agent / synth
```

`agents/*.md`、`schema/handoff.md` 和 `schema/contracts.py` 没有处于这个控制链：编排器是在本进程中**自行构造** Pydantic 对象，而不是校验独立专家的结构化回传。这使“多智能体协作、交接契约、上下文隔离”目前只是说明文档，而非系统性质。

## 3. 关键问题

### P0：合规与安全控制不能作为真实测试的信任边界

1. **没有统一的受控网络出口。** `hermes/tools.py` 直接创建 `httpx.Client(..., follow_redirects=True)`；扫描器、交互式登录、CTF 和利用模块均可调用它。hook 只检查 Claude Code 的 Bash/BashOutput 输入，无法拦截 Python 内部 HTTP 请求。允许的 URL 可以被重定向到 scope 外地址，且没有再次做 host、DNS 解析 IP、scheme、port 和重定向链校验。

2. **`dry_run` 和主动动作可以被环境变量绕过。** `hermes/cli.py` 的 `allow_active()` 接受 `HERMES_ALLOW_ACTIVE=1`，未要求用户批准令牌，也未限制 `platform` 为 local-lab/CTF。`HERMES_CTF_MODE=1` 同样只是环境变量；它可使 `ctf.py`、`exploit_agent.py`、`synth.py` 进入夺旗/利用路径，而没有对真实 Bugcrowd scope 做硬拒绝。

3. **HITL 名义存在，实际未覆盖主动行为。** `Orchestrator.verify()` 将 `needs_active = False` 写死，所有验证对象自动标作 `approved=True`。更早的阶段已经发送 XSS、SQLi、SSTI、命令注入、LFI payload；`interactive.establish_session()` 还会循环尝试十组默认凭据。它们只依赖 dry-run/环境变量，未产生可审计、可消费的一次性人类批准。

4. **`automation_allowed` 和 `rate_limit_rps` 没有被全面执行。** 前者只有 `--recon-only` 分支在 identify 前停止，recon 与 crawl 已发出 HTTP 请求；后者只读取，未传入限速器、HTTP transport 或 CLI。文档“`automation_allowed: false` 不发任何检测请求”的承诺与实现不符。

5. **scope 匹配过宽。** `Scope.is_localhost()` 允许整个 `127.0.0.0/8`，审计实测 `127.0.0.2` 被允许；普通 `in_scope: example.com` 也会匹配任意子域。是否允许这些范围必须显式建模，不能由便利规则隐式扩大。命令 hook 的正则抽取亦不能作为完整网络目标解析器。

**结论：在这些问题修复并以测试证明前，禁止把该运行时连接到真实 Bugcrowd/HackerOne 资产。**它只能作为隔离的本地教学原型，且应默认关闭 CTF/合成能力。

### P1：核心产品能力与报告可信度不成立

1. **不是实际的多智能体系统。** `SKILL.md` 说“经 `Task` 工具分派”，但代码没有 runner、队列、agent 生命周期、独立上下文、失败重试、审批等待、交接验证或专家审计证据。`ThreadPoolExecutor` 并发 scanner 不是专家智能体协作。

2. **候选与已验证发现混淆。** 例如 API scanner 将“未带 Authorization 的 JSON 200”标成 Broken Authentication，验证阶段只是再次检查 200；公共 API 同样会命中。IDOR 仅比较匿名读取 `id=1/2` 的不同响应，没有两名授权测试身份、对象归属或拒绝对照。敏感路径只要 200 且非空就被标高危，可能是 SPA fallback 或登录页面。因而报告里的 `verified` 不是可提交结论。

3. **严重度/VRT/CVSS 是硬编码简化。** `CLASS_SEV` 把类别/置信度映射为 P2–P5；报告既未计算 CVSS，也没有项目级 VRT、业务影响、可利用条件或人工复核状态。生成的 VRT draft 即使失败也会被静默忽略。

4. **大量异常被吞掉。** scanner 注册与运行、爬虫、外部工具和报告生成含广泛 `except Exception: pass`/空列表回退；这会把依赖缺失、超时、scope 问题与真实“未发现漏洞”混为一谈，制造不可解释的假阴性。

5. **CTF/动态合成造成严重的目标漂移。** 当前仓库包含 RCE、反序列化、SSRF、gopher、JWT 爆破、pwn/crypto 解题和 LLM 动态代码执行。即使注释声称仅限 CTF，它们与“Bugcrowd 学习型、最小 PoC、团队 Skill”不是同一个安全等级，也压过了尚未完成的控制面。应拆为独立、离线的 `hermes-ctf-lab` 扩展，不能与真实 engagement runtime 同发行。

### P1：工程可重复性与可维护性不足

1. **零正式测试、无依赖描述、无 CI。** 当前“评分卡”是命令式脚本，不会在提交时自动运行，环境不能重建，README 的“已测试”无法独立复现。

2. **基准不是独立质量证据。** local labs 和 truth 均与 scanner 一同演化；XBOW 以“类别覆盖/检测代理”衡量，而非端到端、独立标注的真实漏洞验证。覆盖百分比不能等价于发现率或准确率。

3. **运行数据污染源码工作区。** 每次 run 固定覆盖 `state/state.json` 与 `report.md`，向 `audit.log` 和知识库直接追加/写入；没有 run ID、输入快照、原子写入、锁、恢复或保留策略。并行模式下 audit 的“append-only”没有跨进程锁保证。

4. **测试脚本本身有危险副作用。** `hermes/benchmarks/local.py` 为固定端口调用 `lsof` 后 `kill -9`，可能杀死不属于本次基准的本地进程。这不能作为安全项目的默认测试行为。

### P2：文档治理问题

- README 过长且以大量“真实夺旗/实测”叙述承担产品规范角色，难以区分演示、可重复基准和设计目标。
- `README.md` 说 skill 已通过符号链接挂载，但审计范围内未发现 `.claude/` 或该链接；此类安装状态不应写成仓库事实。
- 调研报告的来源层级混杂：官方文档、博客和厂商文章未区分；没有版本/访问日期/关键结论到来源的逐项可追溯关系。
- `docs/04` 找出了正确的风险类别，但后续实现没有把它们转为可执行验收测试，因此“批准进入 Phase 0”的裁决被过早地扩大成“Phase 0–3 完成”。

## 4. 重构目标与非目标

### 目标

构建一个可审计、默认保守的 **Hermes 协作式安全评估 Skill**：在授权范围内，真实运行角色化 agent 工作流；将“候选、批准、验证、报告”分离；以一个不可绕过的 policy/transport 层约束所有网络与工具行为；先服务本地靶场和只读 engagement，再逐步扩展。

### 明确非目标

- 不在主项目中提供夺旗、RCE、爆破、payload 绕过、gopher、pwn/crypto 或动态 exploit 合成。
- 不把“200 响应”“模板命中”“模型推测”称为已验证漏洞或可提交 Bugcrowd 报告。
- 不以环境变量、README 文字或 agent 自觉代替批准与策略执行。
- 不在未有独立测试和明确 RoE 的情况下宣称真实项目可用率、精确率或 VRT 分级准确率。

## 5. 建议的目标架构

```text
Skill / Hermes Orchestrator
  ├─ Run plan + immutable scope snapshot
  ├─ Gatekeeper agent (semantic review only)
  ├─ Agent runner (real independent expert invocations)
  │    ├─ recon ──┐
  │    ├─ mapper ─┼─> versioned JSON handoffs -> contract validator
  │    ├─ web/api/authz/infra ─┘
  │    ├─ verifier (only after Approval token)
  │    └─ reporter (only verified evidence)
  └─ Policy-enforced Tool Gateway
       ├─ canonical URL/DNS/IP/redirect scope checks
       ├─ method/risk classification + approval-token verification
       ├─ RoE feature flags, rate/concurrency/budget limits
       ├─ redacted audit event stream
       └─ HTTP/CLI adapters (the only network egress)
```

关键设计决定：

1. **先选定一个真的 agent 运行时。** 若目标是 Claude Code，Skill 应只编排该平台实际支持的 agent/subagent 机制；若要保持 Python 可独立运行，就实现明确的 `AgentRunner` adapter，并把“没有 LLM runner 时”降级为 *single-process scanner mode*，不能继续宣称多智能体。每个 role 只接收最小化的结构化输入，返回带 `run_id`、`scope_digest`、`evidence_refs` 的 JSON。

2. **将所有触网代码收敛为一个 gateway。** 禁止各 module 直接调用 `httpx`/`subprocess`。gateway 在每个请求前后校验 URL、DNS 解析出的 IP、scheme、port、redirect target、速率、并发和预算；拒绝私网/metadata 地址与 scope 不一致的解析结果；将结果以结构化事件审计。

3. **把批准设计成不可伪造的状态机。** `Candidate -> ProposedAction -> Approval(required/approved/expired) -> Execution -> Evidence -> Finding`。主动请求、登录、默认口令、任何 POST、注入探针与外部 CLI 都必须消费一次性批准 token；令牌绑定 run、action digest、目标、风险、有效期和最大请求数，环境变量不能替代它。

4. **将真实性与能力面分层。** `passive inventory`、`safe read-only checks`、`approved active validation` 分成独立 profile；production profile 不加载 CTF/synth 包。CTF 代码若保留，放到独立仓库或独立额外包，并要求 Docker/loopback 隔离和第二个硬门。

5. **将报告变成证据产品。** Candidate、validated、inconclusive 和 blocked 四种状态分开输出；报告只接收带请求/响应、时间、scope/approval、脱敏证明和人工复核结论的 Finding。VRT 映射采用固定版本的官方 taxonomy snapshot；CVSS 仅在输入齐全时计算并标注版本。

## 6. 分阶段实施计划

### Phase R0：冻结风险面并建立基线（先完成）

1. 将 `ctf.py`、`exploit_agent.py`、`synth.py`、`pwn.py`、`crypto.py` 与对应 README 叙述移出主包，保留在隔离的教学实验扩展中；默认安装不含这些代码。
2. 关闭默认口令尝试、注入、nuclei 与所有状态改变动作；现有 scanner 先只生成“检查计划”或候选，不发主动 payload。
3. 新增 `pyproject.toml`（或明确的 `environment.yml`）和锁文件；建立 `src/`、`tests/`、`docs/adr/` 基础布局。不要再依赖“机器上已经有 excavator”。
4. 用 `run_id` 创建 `runs/<run_id>/`，使 state、audit、evidence、report 和知识输入快照全都按运行隔离；停止覆盖根目录的报告与状态。
5. 写 ADR：agent runtime 选择、RoE policy、批准模型、CTF 隔离、数据保留和 benchmark 定义。

**R0 完成判据：** 全测试可在新环境安装；默认命令不产生网络流量；旧 CTF 路径在主包中不可导入/不可启用。

### Phase R1：策略网关与审批状态机

1. 实现 `PolicyEngine`：严格 scope schema（精确 host、显式 wildcard、CIDR、允许的 scheme/port、DNS policy、RoE、rate/budget）。禁止普通域名隐式包含子域；localhost 只允许显式 loopback 地址。
2. 实现唯一的 `Transport`/`CommandGateway`，通过依赖注入提供给工具；静态检查禁止 `httpx.*`、`requests.*`、`subprocess.*` 在 adapter 以外使用。
3. 实现 request plan、risk 分类、approval challenge、带 TTL 的 approval token、审计事件与取消/超时状态；所有 active 行为必须由 gateway 验证 token。
4. 正确实现 `automation_allowed=false`：任何网络请求在连接前拒绝；实现 token bucket 限速和每 run 并发/请求/时长预算。
5. 安装 hook 作为**外层辅助防线**，但不再把它视为 Python 运行时的唯一安全边界。

**R1 完成判据：** scope 外、DNS 重绑定、跳转到 scope 外、禁自动化、超速、缺审批和过期审批的用例都失败且没有出站连接。

### Phase R2：真实多专家工作流

1. 定义 `AgentRunner`、`HandoffEnvelope`、`TaskResult` 和 `EvidenceRef`；Pydantic 模型校验外部回传，不再只是本地对象自检。
2. 给每个 agent 明确输入、输出、允许动作、预算、失败语义和证据职责。Gatekeeper 只能做语义裁决，不能绕过 policy；Reporter 不能把候选提升为 verified。
3. 在 runtime adapter 中真正启动独立专家 invocation，并记录 prompt/工具摘要/结构化回传 hash；没有 runner 时明确显示“单进程规则扫描模式”。
4. 将 scanner 改为产生最小、可审计的 `ProposedAction`；Verifier 在批准后运行并保存正反对照。认证/授权检查必须使用 scope 提供的、具归属关系的测试账号和对象。

**R2 完成判据：** 测试可证明各角色被独立调用、无效 handoff 会阻断阶段、未批准验证不能产生网络动作、报告只能消费 verified evidence。

### Phase R2.5：未知问题的知识学习与受控 wheel 合成

“遇到没有知识基础的特定问题，Hermes 能收集学习并造出 Wheel 解决”是用户在后续开发测试期间正式增加的 v3 需求，**不是 v1 原始提示词内容**。该方向应被定义为核心的**受治理能力扩展**，而不是“LLM 看网页后直接生成并执行任意攻击代码”。当时 `synth.py` 的做法把 LLM 生成代码直接送入受限 `exec`，且由环境变量开启；这不具备来源可信度、可复现验证、人工发布或真实 engagement 隔离，不能作为该能力的最终实现。

#### 6.1 要解决的真实问题

未知问题通常不是“缺一个更强的 payload”，而是缺少以下其中之一：

- 对协议、框架、文件格式、认证流程或业务机制的**可验证解释**；
- 将观察结果转成结构化证据的 parser、decoder、endpoint extractor 或检测规则；
- 适合当前已授权目标、可复现且最小影响的**验证步骤**；
- 一段可复用的适配代码，例如解析特定 API schema、归一化某工具输出、识别某服务版本，或对本地测试夹具执行安全检查。

因此，wheel 的产品定义应是一个**版本化、可审查、可测试、受策略约束的能力包**，而不是一段在生产目标上自由执行的 LLM 代码。首批只允许低风险类别：协议/响应解析器、指纹/版本归一化器、端点/参数提取器、证据脱敏器、报告分类器、被动检查规则和本地夹具验证器。主动探针、认证尝试、绕过逻辑、RCE、爆破、数据提取和任意网络访问不属于自动合成范围。

#### 6.2 受控学习闭环

```text
未知现象 / failed candidate
  -> Knowledge broker：定义问题、风险和所需证据
  -> Researcher：检索允许来源，取得可追溯事实
  -> Planner：形成最小能力规格（不是直接写代码）
  -> Wheel generator：生成候选包 + 测试 + 使用说明
  -> Static/Sandbox validator：离线检查、临时网络隔离验证
  -> Human review / publish：签发版本与适用 profile
  -> Runtime selector：仅按声明能力、scope 与审批调用
  -> Outcome review：记录效果、失败与撤销条件，更新知识库
```

每一步的硬约束如下：

1. **研究不是网页复制。** Researcher 只可从允许的来源获取资料；优先官方标准、供应商安全公告、CVE/NVD/厂商修复说明、正式协议文档和本地源码。每条结论保存 URL、访问时间、版本/commit、许可证、摘录哈希、适用条件和置信度。将外部页面视为不可信数据，不能让其中的指令覆盖系统提示、scope 或审批策略。
2. **先写 capability spec。** Planner 必须产出：输入/输出 schema、允许的副作用、最大请求数、需要的 profile、证据断言、已知反例、失败语义和撤销条件。若规格要求主动请求，先走 Approval 状态机；没有批准时只能生成检查计划和本地测试。
3. **wheel 生成受限。** 生成器输出独立目录，不得修改主运行时或已有 wheel；代码只能调用注入的 `ToolGateway`，不得自行导入 `httpx`、`requests`、`socket`、`subprocess`、文件系统写入或动态 `exec/eval`。默认没有网络、环境变量、密钥和宿主文件系统权限。
4. **先验证后发布。** wheel 必须附带单元测试、反例、fixture/golden data、静态检查结果、依赖 SBOM 和能力清单。仅在临时目录、随机端口、受控本地靶场或离线 fixture 中测试；真实目标上首次使用仍需单独批准。
5. **人审后才成为知识。** 通过验证只是“candidate wheel”；只有人工审批、签名并写入 registry 后才可复用。任何运行失败、误报、异常副作用或来源撤销都可将 wheel 标为 quarantined/revoked，运行时立即停用。

#### 6.3 目标组件与数据模型

| 组件 | 职责 | 关键约束 |
|---|---|---|
| `KnowledgeBroker` | 将未知现象归一为问题卡；检索、去重、评分和引用 | 保留 provenance；不把未可信网页直接喂给执行 agent。 |
| `Researcher` agent | 基于允许来源建立“事实—证据—适用条件”记录 | 只读；输出引用而非可执行命令。 |
| `CapabilityPlanner` | 由知识和当前观察产生 wheel spec、风险分类和测试计划 | 不能批准自己；高风险 spec 只能停在计划状态。 |
| `WheelGenerator` | 从 spec 生成受限插件、tests、文档和 manifest | 无直接网络/命令/动态执行权限。 |
| `WheelValidator` | AST/依赖检查、schema 测试、fixture 与本地隔离集成测试 | 失败默认拒绝；生成完整验证报告。 |
| `WheelRegistry` | 存储内容哈希、签名、版本、来源、适用 profile、能力与撤销状态 | append-only 审计；禁止静默替换版本。 |
| `RuntimeSelector` | 按 target profile、scope、approval 和 manifest 选择 wheel | 只能经 ToolGateway 调用；默认拒绝未知能力。 |

建议每个 wheel 使用如下 manifest（JSON/YAML 均可）：

```yaml
id: protocol-json-parser
version: 0.1.0
kind: passive_parser                 # passive_parser | detector | local_fixture_validator
input_schema: schemas/http-response.json
output_schema: schemas/parsed-observation.json
capabilities: [parse_response]
network: deny
filesystem: read-fixtures-only
profiles: [local-lab, recon-only]
sources:
  - url: https://example.invalid/spec
    retrieved_at: "2026-07-10T00:00:00Z"
    content_sha256: "..."
    license: "..."
tests: [tests/test_protocol_json_parser.py]
artifact_sha256: "..."
status: candidate                  # candidate | approved | quarantined | revoked
approved_by: null
```

这份 manifest 是策略输入，不是说明文字：`network: deny` 和 `capabilities` 必须由 sandbox/runtime 强制，不能由插件自行决定。

#### 6.4 Wheel 的状态机和分级

```text
draft -> researched -> specified -> generated -> validated
      -> candidate -> approved -> active
                               -> quarantined -> revoked
```

- `passive_parser`、`normalizer`、`report_classifier`：可在离线 fixture 验证后进入人工审批。
- `detector`：须包含正反例、假阳性分析和每请求成本；进入真实 scope 前仍由 ToolGateway 限速与 scope 检查。
- `local_fixture_validator`：仅允许 local-lab/CTF 隔离 profile，不能被生产 profile 选择。
- `active_validator`：初期不自动生成；如未来允许，必须单独设计、双人审核、每次 execution approval，并在专用隔离环境先验证。
- `exploit`、`credential_attack`、`exfiltration`、`persistence`：主项目永久拒绝；这不是 wheel 自动化的扩展点。

#### 6.5 防止“学错、造错、复用错”

1. **知识污染与 prompt injection：** 对外部文本做内容隔离，研究 agent 只抽取事实与引用；不得执行页面中的命令、不得相信页面声明的 scope、不得把 HTML/源码直接当作系统指令。
2. **供应链风险：** 禁止 wheel 在运行时安装 PyPI/npm 包；依赖须在构建阶段锁定、扫描、生成 SBOM，并由 registry 引用内容哈希。
3. **幻觉与过拟合：** 任何模型结论都只是 hypothesis；只有通过 fixture、反例与批准的本地验证才可升级。把“未解决”和“证据不足”作为正常结果写入知识库，避免虚假的成功记忆。
4. **记忆越权：** knowledge 记录不得保存真实凭据、token、原始用户数据、可直接复用的攻击 payload 或 scope 外资产；保存脱敏模式、适用条件、证据摘要和已批准 wheel ID 即可。
5. **可撤销性：** registry 按 wheel 版本、来源、数据集和目标 profile 记录影响范围；发现误报或来源被撤回时可一键 quarantine，并让后续 run 失败关闭。

#### 6.6 R2.5 验收测试

1. 给定一份未知协议的离线规范和样例响应，系统能生成 `passive_parser` spec、候选 wheel、正反例测试及 provenance，但不会发出网络请求。
2. 生成代码若导入网络、命令、动态执行或未声明依赖，静态验证必须拒绝；绕过 AST 的行为还须由 sandbox 权限拒绝。
3. 未签名/未审批/已过期/已撤销 wheel 无法被 RuntimeSelector 加载；审批后也只能获得 manifest 声明的 capability。
4. 候选 detector 在含公开 API、SPA fallback、认证页等反例的 fixture 上不会升级为 verified；误报时会生成 quarantine 记录。
5. 外部资料包含“忽略前述规则”“执行此命令”等文本时，research output 只保留引用/风险标记，不改变 policy、scope 或执行计划。
6. 每次 wheel 使用可追溯到 wheel hash、spec、来源 hash、验证报告、审批和 run ID；在临时工作区重复构建得到相同或可解释差异的 artifact。

### Phase R3：检测质量、报告与评估

1. 重写检测器的断言：为 API、IDOR、敏感路径和安全头加入反例与多信号验证；对没有充分证据的结果标为 candidate/inconclusive。
2. 用官方 VRT snapshot 建映射及回归样例；补齐 CVSS 输入 schema、证据脱敏器和人工 review 队列。
3. 建立独立 tests：unit、property/fuzz（URL/scope parser）、contract、gateway integration、agent workflow、e2e local lab；以临时目录和随机端口运行，禁止 `kill -9` 扫端口。
4. 基准采用版本化 fixtures、冻结 truth、独立于 detector 的标注；分别报告 coverage、candidate recall、verified precision、误报、漏报、成本、时延和阻断次数，不能将它们混成“夺旗成功率”。

**R3 完成判据：** CI 在干净环境通过；本地靶场 E2E 可重复；性能/质量数字带数据集版本、命令、配置 hash 和失败记录。

## 7. 优先级排序的重构待办

| 优先级 | 工作项 | 主要位置 | 验收证据 |
|---|---|---|---|
| P0 | 移除主运行时的 CTF/合成攻击路径；默认零网络 | `hermes/ctf.py`、`synth.py`、`exploit_agent.py`、CLI | 没有明确 local/CTF profile 与批准 token 时，任意 active action 被拒绝。 |
| P0 | 统一 Policy + Transport gateway | 新建 `runtime/policy.py`、`runtime/transport.py` | mock transport 证明所有出站请求均经过 policy；redirect/DNS 测试通过。 |
| P0 | 实现审批状态机 | 新建 `runtime/approval.py`、`schema/contracts.py` | 登录、POST、探针、CLI 均缺 token 失败。 |
| P0 | 严格 scope、RoE、rate/budget | `scope.py` 替换为 schema 驱动实现 | `automation_allowed=false` 零网络；rate 有计时测试。 |
| P1 | 实现真实 AgentRunner 或降级命名 | `SKILL.md`、新建 `runtime/agents/` | 调用记录和 handoff JSON 证明角色独立执行。 |
| P1 | 分离 candidate/verified/report | scanners、verifier、reporter | 公共 API、SPA fallback、匿名对象等反例不产生 verified finding。 |
| P1 | 建设受治理的 Knowledge/Wheel 闭环 | 新建 `knowledge/`、`wheels/`、registry、validator | 未审批 wheel 不可运行；生成 wheel 仅在离线 fixture/local-lab 通过验证后可发布。 |
| P1 | 工程化与测试隔离 | `pyproject.toml`、`tests/`、CI | 新环境一条命令装依赖并跑测试；不写工作区产物。 |
| P2 | 文档、ADR、可追溯调研更新 | `README.md`、`docs/01`–`05` | 所有能力声明有测试/基准链接，所有外部结论有版本和访问日期。 |

## 8. 最小验收测试清单

1. 精确 host、显式 wildcard、CIDR、localhost、IPv4/IPv6、URL userinfo、端口、编码 host、DNS rebinding 的 scope property tests。
2. 初始 URL scope 内但 30x 到 scope 外、网页中跳转到 metadata/private IP、DNS 解析变更时，gateway 均不建立连接。
3. `automation_allowed=false`、dry-run、超预算、超速、无 token、token 过期/目标不匹配时，所有 HTTP/CLI actions 都被拒绝并写审计。
4. POST 登录、默认凭据、XSS/SQLi/SSTI/CMDI/LFI probe 必须先生成批准请求；批准前 mock transport 的调用数为零。
5. 伪造/缺字段/错误 scope digest 的 agent handoff 被 schema 拒绝；失败原因可见，不得被空 `except` 吞掉。
6. 对公共 JSON API、公开 object、SPA fallback、无版本 Server header 等反例，不产生 `verified` finding。
7. 使用两个明确授权且不同归属的测试账号/对象，才能验证 IDOR/BOLA；否则只生成测试计划。
8. 报告中每个 verified finding 都能追溯到 scope snapshot、approval、请求/响应哈希、时间与证据脱敏记录；candidate 绝不混入正式发现。
9. E2E 在临时目录、随机端口、隔离网络运行，不杀宿主其他进程，不覆盖工作区文件。
10. CI 覆盖单元、契约、集成和 local e2e；生成可下载的审计/基准 artifacts。

## 9. 最终判断

Claude 版本的主要问题不是“功能少”，而是**把能力堆叠在尚不可靠的控制面之上**：用函数并发冒充 agent 协作，用环境变量冒充审批，用局部 hook 冒充全局策略，用演示靶场成绩冒充真实质量。因此它越扩张，风险和不可信性越高。

重构应采取“先减法、后能力”的路径：先把 CTF/动态利用与真实 engagement runtime 分离，建立可测试的策略网关和审批状态机，再兑现真实的 agent orchestration、证据链和报告质量。只有达到 R1/R2 的验收门槛后，才应恢复主动检测；在此之前，项目定位应诚实写为**本地实验性扫描原型**。
