## 1. 总结结论

项目已经不是早期扫描/CTF 原型：V2 最小纵向闭环、V3 四分支协作与 R2.5 固定被动 Wheel 都有真实
Docker + Hermes ACP 的 localhost 验收工件。最新 V4 也已经实际生成一条 accepted、readonly reject、
完成后幂等 resume 与六类 tamper 阻断工件。

但**不能宣布全部路线完成，也不能进入真实资产评估或正式质量阶段**。主要阻断项是：

1. V4 已有冻结、显式的 320-case ground-truth 质量门和 fresh-preflight 重算，但韧性矩阵的真实
   ACP + Docker 工件尚未齐全；
2. V4 缺少 crash/cleanup、分支失败、两类审批拒绝和完整篡改矩阵的真实 E2E；
3. CI 没有强制运行 V3/V4/R2.5 的真实 ACP + Docker 驱动，不能把手工本机工件当作持续门；
4. PRD、追踪矩阵、README、阶段记录仍把 V4 写成“未验收”，与最新工件和实现状态不一致；
5. 真实资产 profile、通用 Wheel、评估→学习→受控恢复、独立 XBOW/Cybench 质量评估仍未实现或未验收。

本次代码门：`ruff check src tests scripts`、`mypy src`、`pytest -q` 均通过，结果为 **409 passed, 3 skipped**
（2026-08-01；§8.3 为权威基线。演进：原审核记 380/8 → 实跑校正为 386/3 → 本会话依次新增 7 护栏冒烟 +

### 2.2 与原始目标的实际差距

原始文档所要求的不是“自动化攻击包”，而是**在授权、最小动作和人工接管边界内的精密评估团队**。
按这个标准，当前完成度呈现明显的两层：

- **已形成可信局部闭环：** 受限 provider、独立角色、审批/签名、可重放证据、最小验证、并行协作与
  fail-closed 报告均已超过早期 Phase 0–2 的骨架目标。
- **尚未形成产品级全流程能力：** 检测面主要由固定 fixture 语义和固定候选定义，V4 的质量指标尚未经
  独立 benchmark 证明，
  学习闭环不能回到评估，CI 没有强制真实验收，真实资产 profile 仍不存在。

因此，当前合理的完成判断不是一个单一百分比：**“受治理 local-lab 编排与证据链”已接近完成；
“对授权真实资产提供可量化、多领域、可持续学习的安全评估产品”仍有实质差距。** 后一层的首要
收敛项仍是本报告第 5 节的 V4 质量门、韧性 E2E、CI acceptance、独立 benchmark，以及 CAP-07；在
有明确 RoE 和独立真实资产 profile 前，不应以扩大主动扫描能力来填补该差距。

### 2.3 不应被误读为未完成需求的内容

- `docs/01` 中列举的 HexStrike、ProjectDiscovery 与其他高能力 MCP 工具是调研参考，不构成把它们接入
  主包的授权或完成条件。当前 restricted ACP/parent Gateway 的收敛是为了满足原始的合规优先原则。
- 轮子（Wheel）不是 v1 原始提示词内容；v1 仅提出 A8 知识沉淀。Wheel 的来源、审批、无网沙箱和撤销
  是后续 v3 需求，必须继续保持与评估权限分离。
- CTF/XBOW/Cybench 是效果评估的候选基准，不是生产检测能力的替身；历史夺旗结果不能关闭 DET-05。
- “VRT 格式对齐”“内部 evidence-validated”“平台可实际提交”是递进且不同的声明等级；只有最后一级
  需要当期平台规则、RoE 和人工判断。

### 11.4 过程中修复/发现的两个真实问题

1. **环境阻断（已解）**：V4 fixture 的 pin 基础镜像 `python:3.12-alpine@sha256:9ba6…` 在本机是
   `<none>`-tagged（仅 digest），BuildKit 解析该 digest 时反复联网 Docker Hub 而**卡死约 30 分钟**
   （`docker build` 超时）。`docker tag <local-id> python:3.12-alpine` 使其可离线解析后，build 降到 0.1s。
   （复现前置：确保基础镜像有常规 tag，或先 `docker pull python:3.12-alpine`。）
2. **模型可靠性（已缓解）**：`deepseek-v4-flash` 是轻量模型，偶发在 V4 Recon 契约上输出非 schema 载荷、
   schema-repair 后仍失败 → `provider_protocol_invalid`（`retryable=false`），使 `--scenario all` 首次在
   Recon 阶段中止。因 Recon/Mapper 在任何 fault 注入与审批之前运行，其失败必为**前分支的偶发 provider 错误**
   而非注入故障，故在 `run_phase5_e2e.py::_start` 加了**重试为新 run**（默认 4 次，`HERMES_E2E_START_ATTEMPTS`
   可调；commit `18defde`），与工作流 `next_required_action=retry_as_new_run` 一致。加此重试后 `--scenario all`
   成功。同样的重试已镜像到 `run_phase4_e2e.py`（commit 见 git log）。
   同样的重试已镜像到 `run_phase4_e2e.py`。

3. **Phase 4（V3）`accepted-full` 基线的深层问题（经 flash+pro 双跑定位，非纯模型问题）**：该基线场景在
   `_SCENARIO_EXPECTATIONS` 中要求 `coverage: "completed"`（**零 gap**）并硬编码签 `--verdict accepted`。
   实测两种模型都**未能一次产出零 gap 的运行**，但**失败源不同**：
   - **flash**：`infra` 分支**超时**（`branches_timed_out=1`）→ gap；
   - **pro**：4 分支**全部成功**，但候选 `web-xcto` 被判 **inconclusive/needs_more_evidence**
     （`candidates_inconclusive=1`、`gaps=[candidate:web-xcto:needs_more_evidence]`）→ `completion=completed_with_gaps`。
   两次都因 `coverage.completion=completed_with_gaps` 而与硬编码 `accepted` 不符，CLI 正确拒绝
   （`cli_v3.py:392`：`expected=accepted_with_gaps if completed_with_gaps else accepted`）。
   **准确结论**：这**不是单纯 flash 弱**——pro 也 gap 了，只是原因从「分支超时」变成「候选判定 inconclusive」。
   根因是 **`accepted-full` 基线要求零 gap 的运行，而当前工作流+模型对每个候选的验证判定是模型敏感的**
   （web-xcto 是否 validated 取决于 **cross-review 的 verdict**：`campaign_v3.py:311` 中 `needs_more_evidence`
   → inconclusive → gap；父运行时确定性重算的是 header/status/body 等事实，但 concur/needs_more_evidence 的
   质量判定由 cross-review 模型给出，故非确定性 bug、也不应绕过该质量门）。真实评审会按实际 coverage 签 `accepted_with_gaps`，
   但该 driver 场景刻意断言干净 `completed`。**因此 V3 `accepted-full` 在本会话两种模型下均未一次通过**；
   收敛选项（留给用户决定）：(a) 重试直到模型对全部候选给出 validated（模型敏感、非确定）；(b) 若产品语义允许
   基线接受 gap，则让 driver 按实际 coverage 自适应签 verdict（会改变该场景「验证零 gap 干净运行」的原意）；
   (c) 提高候选验证的确定性（父运行时对 web-xcto 这类可确定性重算的候选强制 validated，减少模型判定空间）。
   **诚实边界**：历史 Phase 4 验收记录为 4 findings/`completed`。**后续重试证实这与历史一致、非硬漂移**：
   第三次运行（pro）得到全 concur 的干净运行——16 task、15 evidence、14 consumption、**4 findings**、fixture
   restored、`--verdict accepted` 匹配通过（根 `20260802T055255Z-…`）。所以 `accepted-full` **可以**通过，只是
   零-gap 依赖 cross-review 对全部候选 concur，属**模型敏感的非确定性**；单次是否通过随模型判定波动，重试即可
   得到干净运行。这仍暴露一个真问题：**CI 未覆盖真实 E2E**，故这类模型敏感/契约漂移（含 §11.2 的 schema-version
   回归）只有真跑才暴露。
