# Hermes 战争迷雾理解推理报告

> 生成方式：主智能体独立「走图」+ 子智能体文档研读作为补充参考
> 生成日期：2026-08-01
> 独立核查范围：`docs/01`–`15` 全部权威/历史文档、`src/hermes/**`、`scripts/**`、`hooks/**`、`.github/workflows/**`、`artifacts/**` 真实工件、`tests/**`（389 用例 collect）
> 方法：以「战争迷雾」推理——先钉死迷雾两端（起点=已知、终点=预期效果），再逐节点点亮，判断**当前实现能否穿过每一段迷雾**，标注更优实现与偏离路径。所有结论均给出真实存在的证据路径。

---

## 0. 方法论：为什么用「战争迷雾」

这个项目的文档极多（15 份权威/历史文档 + ADR），彼此存在**权威关系、过期、重复**三种张力。若按文档顺序线性阅读，很容易把「文档声称」当成「已经做到」。战争迷雾方法强制我做两件事：

1. **钉死两端**——起点是什么（v1 原始意图 + 早期骨架），终点是什么（PRD 1.6 定义的两条闭环）。两端之间才是需要点亮的迷雾。
2. **逐节点验证能否穿过**——每个链路节点，不看文档怎么说，而看代码/工件是否真的让「上一节点的输出」安全地流到「下一节点」。凡是「文档点亮了但代码里是黑的」，就是幽灵；凡是「代码点亮了但文档还是黑的」，就是隐藏功能或过期文档。

## 1. 迷雾的两端

### 1.1 起点（已知的初始态）

| 维度 | 初始态 | 依据 |
|---|---|---|
| 产品意图 | 以 **Skill** 为交付形态，由 Hermes 编排多个**独立专家智能体**，完成「侦察→测绘→识别→最小验证→报告→知识沉淀」的受控评估 | `docs/01`–`03`、`docs/08` §2 v1 行 |
| 安全底座 | v2 追加：scope/RoE 冻结、唯一 Gateway、一次性审批、run 隔离、Candidate/Validated 分离、证据脱敏、人工复核 | `docs/08` §2 v2 行、§5 |
| 学习底座 | v3 追加：未知问题→研究→Wheel→沙箱→签名→复用→撤销 | `docs/08` §2 v3 行、§6.3 |
| 靶场 | 固定 localhost 教学 fixture（`missing_x_content_type_options` 等） | `docs/08` §9 |

### 1.2 终点（预期效果）

PRD 1.6（`docs/08` §1）把预期效果定义为**两条相互衔接的闭环**：

- **安全评估闭环**：授权确认 → 侦察 → 测绘 → 多领域分析 → 候选发现 → 审批 → 最小验证 → 人工复核 → 报告。
- **能力学习闭环**：识别缺口 → 研究可信资料 → 能力规格 → 生成候选 Wheel → 离线+沙箱验证 → 人工签名审批 → 受控复用 → 效果反馈与撤销。

并且叠加三条不可混用的交付等级（`docs/08` §4.5）：**VRT 格式对齐 < 内部 validated < 平台可实际提交**。

### 1.3 迷雾之外的红线（永久非目标，不需要点亮，反而要确保「保持黑暗」）

未授权测试、DoS、外泄、持久化、检测规避、真实凭据攻击；主包内不得有夺旗/RCE/爆破/任意利用生成；agent/网页/模型/env/Wheel 不得改变 scope/审批/策略（`docs/08` §4.6、§5）。**独立核查结论：这条红线在代码层面守住了**——`grep` 全 `src` 仅 1 处 `NotImplementedError`（抽象基类 `runtime/agents/runner.py:65`），无利用代码；CTF 能力被隔离在 `extensions/hermes_ctf_lab`（`docs/07` 不变量 4）。

## 2. 主链路逐节点点亮（安全评估闭环）

对每个节点给出：**预期 → 当前实现 → 独立证据 → 能否穿过迷雾 → 更优/偏离**。

### 节点 A：授权与 Scope 冻结（GOV-01）
- **预期**：录入并冻结 RoE，严格校验 host/wildcard/CIDR/scheme/port/DNS/profile/自动化许可。
- **当前实现**：`runtime/policy.py` + `runtime/context.py`；固定 scope 快照 `scope.yaml`。
- **独立证据**：`scope.yaml` 存在；每个真实工件根都带独立 `scope.yaml`（如 `artifacts/phase5-e2e/20260801T075539Z-.../scope.yaml`）。
- **能否穿过**：✅ 对 localhost。**迷雾未散处**：真实域名 RoE/自动化/限速/身份的产品级 profile 不存在——只能生成「零网络计划」。
- **偏离/更优**：无偏离。这是全项目最扎实的节点。

### 节点 B：唯一工具网关（GOV-02）
- **预期**：网络/DNS/命令/凭据只能过受策略约束的 Gateway。
- **当前实现**：`runtime/gateway.py` + `runtime/transport.py`（pinned loopback transport）。
- **独立证据**：`tests/test_pinned_transport.py`；真实 E2E 工件中 HTTP evidence 均带 manifest。
- **能否穿过**：⚠️ **半程**。HTTP Gateway/pinned transport 真跑通了；**命令输出 broker、凭据 broker 尚未闭环**（`docs/09` GOV-02 明确「部分实现」）。
- **偏离/更优**：设计正确，缺口是「命令/凭据」这一路还没接到真实执行面。

### 节点 C→D：侦察 → 测绘（DET-01）
- **预期**：对资产/路由/参数/认证入口/服务/配置形成有 coverage 的结构化清单。
- **当前实现**：`vertical.py` / `vertical_v3.py` 的 Recon/Mapper 角色。
- **独立证据**：V2 accepted 工件里 Recon 1 GET + Link/GraphQL/debug/identity 元数据映射；V4 主根 `.../runs/d6244c09-.../` 下有 `discovery_v4/`。
- **能否穿过**：✅ 对 fixture。**迷雾未散处**：只对**受信元数据/固定 Link/OpenAPI**测绘，不是开放世界 recon。父运行时从 hash-bound `analysis.json` 重算安全事实（`docs/08` §5.8），这一点做得比多数扫描器都严谨。
- **偏离/更优**：无偏离；开放世界资产发现是明确的未来项，不是缺陷。

### 节点 E：多领域候选分析（DET-02）
- **预期**：Web/API/Authz/Infra 专家产出带反例和所需证据的 Candidate，不因单模板命中升级。
- **当前实现**：`collaboration_v3.py` 四分支；V4 用 `campaign_v4.py`/`discovery_v4.py`/`verification_v4.py`。
- **独立证据**：Phase 4 accepted `81764e3a-...` 中 5 个原始候选确定性去重为 4 个规范候选（XCTO/GraphQL/Authz/debug）。
- **能否穿过**：✅ 对四种固定候选族。**迷雾未散处**：任意漏洞族未覆盖。
- **偏离/更优**：**这是全项目最漂亮的机制**——真正的 fan-out/fan-in + 环形交叉复核 + 去重。但要清醒：它证明的是**协作机制精密**，不等于**各安全领域都有专家能力**（`docs/15` §2.1 已自省）。

### 节点 F：HITL 审批（GOV-03）
- **预期**：challenge / 明确批准拒绝 / 暂停 / 过期 / 恢复；审批人与执行者分离。
- **当前实现**：`vertical_contracts.py` + `security.py`；Ed25519 一次性 approval bundle。
- **独立证据**：`tests/test_phase2_security.py`；V4 主根同时存在 accepted（`d6244c09`）与 **readonly reject**（`47f06cc3`，仅 2 份无审批 evidence、无正式报告）两条工件。
- **能否穿过**：✅。Approver/Reviewer 分钥、一次性 consumption、跨 Gateway 重放拒绝都真跑通了。
- **偏离/更优**：无偏离。这是「安全优先于能力」原则落地最好的地方。

### 节点 G：最小主动验证（DET-03）
- **预期**：RoE 允许且逐次审批时，Verifier 用正反对照+最小请求证明/否定候选。
- **当前实现**：`campaign_v3.py` / `ledgers_v3.py` / `verification_v4.py`。
- **独立证据**：Phase 4 中 14 个原子 consumption、15 次总请求、正反对照 + 补偿恢复。
- **能否穿过**：✅ 对固定签名 approval。**红线守护**：PRD 明确写「这是未来目标，不是当前真实资产承诺」（`docs/08` DET-03）。
- **偏离/更优**：无偏离；边界表述克制且诚实。

### 节点 H→I：人工复核 → 报告硬门（GOV-05 / DET-04）
- **预期**：Candidate/blocked/inconclusive 与 ValidatedFinding 分离；报告前从 canonical artifacts 逐项重验。
- **当前实现**：`promotion*.py` + `preflight*.py` + `reporting*.py`；统一 ReportPreflightVerifier。
- **独立证据**（我亲自核对 V4 主根 `20260801T075539Z-...`）：
  - `tamper-summary.json`：`approval_signature / review_signature / consumption_action / coverage / outcome / action_ledger` **六类全部 `blocked_before_reporter`**；
  - `recovery.json`：`completed_run_idempotent_restart`，provider_records 24→24，`resumed_without_new_model_or_network_work`；
  - accepted run `state.json`：`cleanup_state: restored`。
- **能否穿过**：✅ 且**这是整条链的「护城河」**——篡改任一环都会在 Reporter 启动前 fail-closed，正式报告数为 0。
- **偏离/更优**：无偏离。这是把「模型声明不是证据」落到实处的核心保障。

**主链路小结**：从授权到报告，**九个节点里七个已对固定 localhost 教学 fixture 完全点亮**，两个半程（GOV-02 命令/凭据 broker、DET-03 真实资产承诺被有意留黑）。**穿不过的不是链路本身，而是链路尽头那堵墙——「固定 fixture → 真实资产」。**

## 4. 版本演进的迷雾与那堵反复出现的墙

把 V1→V2→V3→V4→R2.5 排开，会看到**同一堵墙反复出现**：

```
V1 教学fixture(只读基线)
  └─ V2 最小纵向闭环 ── [已对固定localhost点亮] ── 墙：真实资产?
       └─ V3 四分支并行协作 ── [已对Phase4 fixture点亮] ── 墙：多资产/任意路由?
            └─ V4 检测与报告 ── [主路径已点亮, 质量门/韧性矩阵半亮] ── 墙：独立benchmark?
                 └─ R2.5 被动Wheel ── [已点亮] ── 墙：CAP-07恢复?
```

**关键洞察**：每一代的「已验收」后面都紧跟同一句限定——**「仅固定 localhost 教学 fixture」**。这不是五堵不同的墙，而是**同一堵墙（固定 fixture → 真实资产/独立质量证明）在五个位置的投影**。因此判断项目完成度，不该问「V4 做完没有」，而该问「**有没有任何一处真正穿过了这堵墙**」——目前答案是**没有，也不应该在缺 RoE/独立 profile 时强行穿过**（`docs/08` §4.6、`docs/15` §2.2）。

## 5. 迷雾中的暗礁：独立发现的偏离、过期与风险

这些是**逐节点走图时新点亮、而文档（含 doc 15）尚未完全反映**的东西。

### 暗礁 1：doc 15 自身的时间戳落后于工件（最重要）
- `docs/15` 保存于 **Aug 1 18:38**；它把 V4 最新根写成 `20260801T075539Z`（07:55），并断言「**V4 真实韧性验收矩阵仍是未完成硬门**」。
- 但 `artifacts/` 里存在**晚于 doc 15 写作时间**的工件：
  - `phase5-resilience-e2e/20260801T105759Z-...`（创建于 **18:58**）——`fault-injection/mode.json = {"fault":"cleanup-failure"}`，含 `resilience_faults/api-graphql-cleanup.json`，一个 faulted run `cleanup_state=required`（fail-closed 正确）；
  - `phase5-resilience-e2e-rerun/20260801T112319Z-...`（创建于 **19:23**）——`mode.json = {"fault":"api-assessment-failure"}`；
  - `phase5-e2e-stability/20260801T114044Z-...`（创建于 **19:40**）。
- **推理结论**：doc 15 的「P0 韧性矩阵未完成」在**写作当时是准确的**，但**已被随后的运行推进**：`cleanup-failure` 与 `api-branch-failure` 两个场景现已各有真实工件。**然而**——这三个新工件的 `tamper/` 目录**全为空**，`run_phase5_resilience_e2e.py` 的 `tamper-matrix` 场景尚未产出，也没有一个 `--scenario all` 的权威根。**所以 doc 15 的最终结论（P0 尚未闭合）仍然成立，只是它的「现状快照」已落后约 3 次运行。** 这正是「地图过期」型迷雾——需要在 doc 15 里回写。

### 暗礁 2：硬护栏 hook 存在但未启用，且路径硬编码
- `hooks/guardrail.py` 是一个**确定性、不经 LLM** 的 PreToolUse 护栏（scope 校验 + 危险命令黑名单 + 状态变更灰名单→ask + dry-run）。设计正确，正好修补 `docs/04` 指出的「用可绕过的 LLM 当硬边界」矛盾。
- **但**：全项目**找不到任何 `.claude/settings.json`** 已合并该 hook；启用完全依赖手动把 `hooks/settings.snippet.json` 合并进去。
- **额外风险**：snippet 里的解释器路径**硬编码**为 `/Volumes/Samsung/conda/envs/excavator/bin/python`——与项目实际使用的 `.venv/bin/python` 不一致。用户若照抄启用，可能因解释器缺依赖而静默失效。
- **与记忆一致**：记忆记录「护栏 hook 待手动启用」——独立核查确认，且**补充了「硬编码路径」这一 doc 15 未提的隐患**。

### 暗礁 3：CI 不强制真实 E2E + 权威文档过期
- `.github/workflows/ci.yml`：只无条件跑 `ruff` / `mypy` / `pytest`（含 integration），`provider_e2e` 仅在 `HERMES_REQUIRE_PHASE2_E2E==1` 时跑。**完全不触发 phase4/phase5/r25 真实 ACP+Docker**。
- `.github/workflows/localhost-acceptance.yml`：面向受保护的 `self-hosted, hermes-acceptance` runner，会顺序跑 V2/V4/resilience/R2.5，但它是**手动 workflow，未设为 required 分支检查，也无远端运行记录**。
- **README 严重过期**：仍写「当前完成门为 `299 passed / 3 skipped`」（`README.md:38`）——而 doc 15 自己说 380/8，子智能体**实跑** `pytest` 为 **386 passed / 3 skipped**（我 `--collect-only` 得 389 = 386 pass + 3 skip，自洽）。全仓库测试基线互相矛盾（README 299、`docs/11` 173、`docs/14` 367、`docs/15` 380），无一为真。
- **推理结论**：doc 15 的 P0「回写文档」与 P1「CI 产品门」两项**完全准确且被独立证实**；README 是其中最刺眼的过期点。

### 暗礁 4：幽灵功能与隐藏功能扫描
- **幽灵功能（文档写了、代码没有）**：仅 **CAP-07**一处（评估暂停→学习→原地恢复）。文档已诚实标注未实现，故属「已披露的缺口」而非「误导性幽灵」。未发现被夸大成已完成的幽灵功能。
- **隐藏功能（代码有、文档弱记录）**：
  - `hooks/guardrail.py` 这层确定性护栏在权威 PRD（`docs/08`）中仅以「hook 仅是外围辅助」一笔带过，其**具体黑/灰名单规则、dry-run 语义、启用方式**没有进入任何验收文档；
  - `scripts/run_phase5_resilience_e2e.py` 的**四场景故障注入框架**（`api-branch-failure`/`mutation-crash-recovery`/`cleanup-failure`/`tamper-matrix`）已成型，但 doc 15 只把它描述为「未完成硬门」，未记录**驱动本身已实现、只差跑全 `all` 矩阵**这一事实。

### 暗礁 5：可复现供应链（NFR-06）
- `requirements.lock` 仅固定顶层依赖、**无 hash**（`docs/09` NFR-06 已标「部分实现」）。独立确认属实。这不是暗礁，而是对既有诚实标注的复核通过。
