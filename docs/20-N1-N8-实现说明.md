## N1 — ScopeProfile 契约 + Bugcrowd 摄取 + 人工签核

**流程（全人工）**：
```bash
# 0) 先手动获取需要的外部仓库（后台运行）
./scripts/fetch_external_repos.sh          # clone Cybench + Bugcrowd VRT 到 $HERMES_EXTERNAL_REPOS

# 1) 把一个 Bugcrowd program 的 scope 导出为 program.json（BugcrowdProgramSpecV1 形状），摄取为草稿
python scripts/bugcrowd_scope_profile.py ingest --spec program.json --out draft.json
#    -> 打印 in_scope_hosts / automated_testing_allowed / dry_run / rate_limit，**人工复核**

# 2) 用 scope 授权私钥（KeyUsage.scope_approval）签核
python scripts/bugcrowd_scope_profile.py sign --draft draft.json \
       --key approver.pem --key-id scope-approver --out signed.json

# 3) 对照 trust store 验证并查看 N1 门
python scripts/bugcrowd_scope_profile.py verify --signed signed.json --trust-store trust.json
```

**Fail-closed 不变量**（`test_scope_profile.py` 全覆盖）：
- 仅 in-scope 的 website/api 目标成为 `ScopeRule`；越界/移动端目标丢弃而非猜测；
- `automated_testing_allowed=false` 的 program → `automation_allowed=false` 且强制 `dry_run=true`（永不主动扫描）；
- `allow_private` 恒为 false（真实 program 不碰私网/回环）；
- 未签核/验签失败 → 授权任何东西都失败；操作 `APPROVAL` 密钥**不能**授权 scope（`SCOPE_APPROVAL` 分权）；
- `submit_requires_human` 恒为 True，`require_human_submission()` 恒抛错（N7 提交红线写死在契约里）。

**给后续节点的接口**：`require_active_scanning_authorized(signed, trust_store, now)` 是进入 N2/N4 主动节点前的硬门；
`authorize_target(draft, url)` 做逐 URL 的 scope 成员/scheme/port/私网校验。二者都返回/校验受签 profile。

## N8 — 独立基准可信度门

**运行（self-hosted runner，operator 先产出 Cybench 结果）**：
```bash
# operator 在 runner 上用克隆的 Cybench 跑基准，产出 per-task 结果文件（映射为下述形状）：
#   {"benchmark":"cybench","model":"...","tasks":[{"id":"t1","solved":true,"subtask_fraction":1.0}, ...]}
python scripts/run_cybench_baseline.py --results tasks.json \
       --min-solve-rate 0.10 --min-tasks 30 --artifact-root artifacts/benchmark
#   pass -> 退出码 0；blocked（样本不足 / 解率低于门）-> 退出码 3，CI 失败
```

**语义**：`evaluate_benchmark_gate` fail-closed —— 基准不匹配、样本 < `min_total_tasks`、或解率 < `min_solve_rate` 都判 `blocked`。
`require_credible(result, gate, now)` 是主动节点在触碰真实 program **之前**要过的可信度门：无 in-date、达标的基准 → 拒绝真实资产主动测试。

**CI 接线**：`localhost-acceptance.yml` 新增可选输入 `include_cybench`（默认关，hours 级）。开启后，若 repo var `CYBENCH_RESULTS`
指向一份结果文件，则跑 `run_cybench_baseline.py` 门控；blocked 使该 job 失败。产出结果文件（用 `CYBENCH_ROOT` 的 Cybench）是 operator 步骤。

## N2 — ProjectDiscovery recon → 受 scope 授权的真实资产清单

**关键设计决定**：现有 `EndpointInventoryV3` 的 `canonical_url` 走 `_localhost_url` 校验——**硬性只允许 localhost**，
这是保护「教学 fixture ≠ 真实资产能力」诚实边界的刻意锁。真实 Bugcrowd URL **进不去** V3 清单。故 N2 产出一个**独立的
真实资产清单** `ReconInventoryV1`（`src/hermes/recon_adapter.py`），并用 `to_endpoint_inventory_v3()` **显式拒绝**桥接进
V3（抛错说明「V3 流水线是 localhost-only，真实资产映射待 N3/N4」）——边界写死在代码里，不伪装。

- `parse_httpx_line` / `parse_katana_line`：容错解析真实 ProjectDiscovery 输出（httpx `-json` 的 `url`/`status_code`/`content_type`/`tech`；katana `-jsonl` 的 `request.endpoint`/`method`）。
- `build_recon_inventory(...)`：**每个端点必须过 N1 `authorize_target`**（对已验签的 ScopeProfile 草稿）——越界/私网/回环一律丢弃并记入 `dropped_out_of_scope`（fail-closed）；每个端点带 `EvidenceArtifactRef`（sha256 绑定到产出它的 recon 记录字节）；按 url#method 去重；`scope_profile_digest` 绑定到授权它的 N1 profile。
- 关系推断（确定性）：path 含 graphql→`graphql`；login/oauth/auth/token→`auth`；json→`api`；html→`web`；否则 `other`。

**驱动** `scripts/recon_to_inventory.py`：先 `require_active_scanning_authorized`（recon 是主动步骤——无已签且授权主动测试的
profile 就拒绝产出清单），再解析 httpx/katana JSONL → 写 `inventory.json` + 每端点 `evidence/<id>/manifest.json` + `summary.json`。
```bash
python scripts/recon_to_inventory.py --signed signed.json --trust-store trust.json \
       --httpx httpx.jsonl --katana katana.jsonl --out-dir artifacts/recon/<program>
```
**红线**：N2 只**消费**已产出的工具输出并按签署 scope 授权；**运行** subfinder/httpx/katana（会发请求）本身是须先经 N1 授权 + 走
限速的主动步骤（后续接 Gateway）。`test_recon_adapter.py` 9 例覆盖 scope 门/私网拒绝/证据绑定/关系推断/拒绝桥接 V3。

## N3 — nuclei 命中 → 受纪律约束的候选集

**核心是「收敛回 Hermes 纪律」**（`src/hermes/candidate_source.py`）：外部黑盒引擎（nuclei）**扩大候选来源**，但输出必须回到 Hermes 的纪律才有意义。
- **candidate ≠ finding**：`CandidateStatusV1` 刻意**没有 `validated`**；`status` 恒为 `candidate`、`requires_active_verification` 恒 `True`——单条模板命中不是证明，须经 N4 最小主动验证（带反例）+ GOV-05 人工复核才配升为 ValidatedFinding。
- **绑定 N2 inventory（= 授权 scope）**：每个候选必须落在 N2 `ReconInventoryV1` 的某端点上；host 不在 inventory 的命中一律丢弃记入 `dropped_out_of_inventory`（fail-closed）。
- **可证伪**：每候选带 `expected_assertion`（验证测试须复现什么）+ `negative_control_hint`（对照）——不因单命中自动升级。
- **无利用载荷**：候选只含假设 + 证据 + 可证伪信息，无 exploit payload（红线；探索/利用类隔离 `extensions/`）。
- **provenance 链**：`CandidateSetV1` 绑定 `recon_inventory_digest`（N2）+ `scope_profile_digest`（N1）——N1→N2→N3 数字摘要成链。
- `parse_nuclei_line`（真实字段 `template-id`/`info.severity`/`matched-at`）；`claimed_severity` 保留 nuclei 严重度但显式标「claimed」；`require_verification_before_promotion()` 守卫：谁想把候选当 finding 就抛错。

**驱动** `scripts/nuclei_to_candidates.py`：nuclei JSONL + N2 inventory.json → `candidates.json` + 每候选 `evidence/<id>/manifest.json` + `summary.json`。
```bash
python scripts/nuclei_to_candidates.py --inventory artifacts/recon/<program>/inventory.json \
       --nuclei nuclei.jsonl --out-dir artifacts/candidates/<program>
```
**红线**：N3 只**收敛**已产出的 nuclei 输出；**运行** nuclei（会发请求）本身须先经 N1 授权 + 走 Gateway 限速（属 N4）。`test_candidate_source.py` 8 例覆盖 status 恒 candidate/绑定 inventory/证据/去重/可证伪/拒绝越界/升级守卫。

## N4 — 最小、经审批、正反对照的验证 → ValidatedFinding

N3 候选只是假设；在 N4 只有走完 Hermes 全套纪律才升为 `ValidatedFinding`（`src/hermes/verification.py`）：
- **正反对照**：计划两个最小探测（候选 + 匹配的反例控制）+ 一个结构化 `VerificationSignalV1`（`header_absent`/`header_present`/`status_equals`/`body_contains`）。裁决**确定性**：候选命中信号且控制**不**命中 → `validated`；候选不命中 → `disproved`；两者都命中（控制不干净）→ `inconclusive`。
- **逐次人工审批**：计划须人工签署（Ed25519，`KeyUsage.APPROVAL`）方可执行；`require_execution_authorized` fail-closed（审批匹配该计划、未过期、密钥可信、两个探测 URL 仍在签署 scope 内）。
- **读多写少、禁破坏性**：`DELETE` 禁用；默认只读（GET/HEAD/OPTIONS）；变更类探测须带补偿计划（`compensation_plan`）否则拒绝。
- **finding 须复核**：`promote_to_finding` 仅从 `validated` 结果 + 第二个人的复核签名（`KeyUsage.HUMAN_REVIEW`）产出 `ValidatedFindingV1`（复核人≠审批人由调用方分权）。

**驱动** `scripts/verify_candidate.py`：`plan`→`approve`→`decide`→`promote` 四步人工工作流。端到端 N1→N2→N3→N4 冒烟过：候选 `exposed-git-config` 经计划/审批/裁决(validated)/复核 → `ValidatedFinding`。
```bash
python scripts/verify_candidate.py plan --candidates candidates.json --candidate-id <id> \
    --signed signed.json --trust-store trust.json \
    --signal-kind status_equals --signal-arg 200 --control-url <in-scope 控制URL> --out plan.json
# approve（APPROVAL 密钥）→ decide（+两份观测）→ promote（HUMAN_REVIEW 密钥）
```
**红线（关键边界）**：模块**计划/门控/裁决**，但**不发请求**。真正发那两个请求是 live 主动步骤，须走受治理 Gateway、受签署 scope + 限速约束；**真实资产的 GOV-02 命令/凭据 broker 仍半程**（`docs/16` 节点 B）。观测由授权的 Gateway 请求产出后喂给 `decide`。`test_verification.py` 10 例覆盖 scope 绑定/只读默认/变更需补偿/审批门/过期拒绝/三种裁决/复核后升级/拒绝未验证与未授信复核。

## GOV-02（真实资产）— 受治理出口：让 N2/N3/N4 能 live 跑

N2/N3/N4 的模块都「只计划/判定、不发请求」。`src/hermes/governed_egress.py` 是让它们**对已授权真实靶标 live 运行**的接缝，
且在**出口时刻**逐请求 fail-closed 治理：
- **scope**：每个出站请求过 N1 `authorize_target`（越界即拒并审计）；
- **自动化门**：scope 未授权自动化 / `dry_run` → 构造即拒（`GovernedEgress.__init__`）；
- **限速**：`_Pacer` 用注入时钟按 `1/rps` 最小间隔间隔请求（确定性可测）；
- **预算**：`max_requests` 用尽即拒；
- **无破坏**：`EgressMethod` 类型层排除 `DELETE`；
- **审计**：每请求一条 `EgressAuditRecordV1`（request/scope 摘要、allowed、reason、waited、status）；
- **凭据零通过**：`EgressRequestV1` 不含任何 secret，审计不记凭据——认证测试是 operator 的 transport（自有授权会话）之责，符合「Hermes 不明文处理凭据」红线。

**网络在 `Transport` Protocol 之后**：测试注入 fake transport + fake clock 确定性覆盖每条治理边；生产传真实 pinned HTTP transport + 真实时钟——**同一条受治理代码路径**。
`execute_verification_plan(plan, egress)` 把 N4 计划的两个探测经受治理出口发出 → 两份 `ProbeObservationV1` → `decide_verification`，**离线闭合 N4 live 环**（测试里 candidate 200 无头/control 200 有头 → validated，两请求均审计在 scope 内）。
这是 localhost-locked `GovernedGatewayV3` 的**真实资产分身**（additive，教学 fixture 不受影响）。

**仍未做**：把**真实 pinned HTTP transport** 接上并指向**真实授权靶标**（= operator 拿到真实 program 授权后的 live 步骤；本仓不含也不应含指向任意真实资产的网络代码）。至此 N2→N3→N4 的受治理执行路径已具备，只差真实 transport + 真实授权目标。

## N7 — ValidatedFinding → Bugcrowd VRT/CVSS 报告草稿（人工提交）

最后一个能力节点（`src/hermes/report_draft.py`）：N4 的 `ValidatedFinding` → **符合 Bugcrowd 分类**的报告草稿。
- **VRT 分类**：`load_vrt_priorities` 从**真实克隆的** VRT taxonomy（`vulnerability-rating-taxonomy.json`，695 个带优先级节点）建 id→priority(1..5) 索引；`vrt_category_id` 须存在于 taxonomy（否则拒），据此得 `P1–P5`。
- **CVSS v3.1**：`cvss_v31_base_score` 实现标准公式（参考向量核对：C:H/I:H/A:H=9.8、C:L=5.3、stored-XSS UI:R/S:C=6.1、0.0），`parse_cvss_vector` 解析 `CVSS:3.1/...`，`cvss_severity` 分档；复用现有 `CvssV31Input` 生成 vector。
- **不编造**：分类是**校验**非发明；narrative（title/summary/steps/impact）由 operator 依证据撰写，Hermes 只组装 + 绑定 provenance（`finding_digest`/`plan_digest`/`outcome_digest`，要求 finding 绑定该 plan+validated outcome）。
- **永不提交（红线）**：`ReportDraftV1.submitted` 恒 `Literal[False]`，`require_human_submission()` 恒抛错；**无 `submit()`**。`render_markdown` 出的 report.md 头部即标 `DRAFT — reviewed and submitted by a human, never by Hermes`。

**驱动** `scripts/finding_to_report.py`：finding+plan+outcome + 真实 VRT + narrative + `--cvss` → `draft.json` + `report.md`。端到端 N4→N7 冒烟过（finding→`full_path_disclosure` P5、CVSS 5.3 medium、provenance 绑定、标 DRAFT、`submitted:false`）。
```bash
python scripts/finding_to_report.py --finding finding.json --plan plan.json --outcome outcome.json \
    --vrt "$BUGCROWD_VRT_ROOT/vulnerability-rating-taxonomy.json" --vrt-category full_path_disclosure \
    --cvss "CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N" --title ... --summary ... --step ... --impact ... \
    --out-dir artifacts/reports/<program>
```
**红线**：Hermes 生成草稿并绑定证据/provenance，但**提交永远由人**（自动/批量提交违规且被平台封号）。`test_report_draft.py` 7 例覆盖 CVSS 参考向量/优先级/provenance 绑定/拒绝未知 VRT 类/草稿标记/提交守卫。

## 增强项（全链验证 + 便利入口）

- **全链组合集成测试** `tests/test_bugcrowd_pipeline_e2e.py`（1 例）：把 N1→N2→N3→N4→N7 每个真实模块**依序串起来**，N4 live 环经 `GovernedEgress`+`ReplayTransport`（GOV-02）跑，断言整条 **provenance 摘要链**（scope→inventory→candidate_set→plan→outcome→finding→draft 全部对齐 `draft.digest()`），离线确定性、不碰 localhost（真实资产链按设计禁回环）。

## 边界与「诚实」声明
- 本次只做**治理契约 + 门控 + 人工工作流**：N1 决定「能不能、对谁、在什么策略下」主动测试；N8 决定「检测可信度够不够格」。
